## ۳) بهترین گزینه کمربیسک: `python-dateutil`

**مسئله:** وظایف تکرارشونده نیازمند قواعد RFC 5545 هستند (`FREQ=WEEKLY;BYDAY=MO,WE`).
پیادهسازی دستی این قواعد (منطقه زمانی، DST، شمارش، استثناء) پرخطاست.

**چرا این گزینه:** Pure-Python، فقط `six` بهعنوان وابستگی، ۱۵+ سال نگهداری،
استفادهشده در پروژههای زیاد. فراداده GitHub مجوز را `NOASSERTION` گزارش کرد، ولی
فایل `LICENSE` از طریق `/repos/dateutil/dateutil/license` دریافت و بررسی شد:
متن استاندارد Apache-2.0 بههمراه اعلامیه dual-license BSD-3-Clause برای مشارکتهای
قبل از ۲۰۱۷. هر دو مجوز permissive و سازگار با استفاده/تغییر/توزیع هستند.

**نحوه ادغام (Adaptation, not copying):**
- هسته کتابخانه دستنخورده است؛ فقط بهعنوان وابستگی `python-dateutil>=2.9,<3` اضافه شد.
- تمام شخصیسازی در یک تابع باریک `expand_recurrence()` در `app/planning/engine.py`
  قرار دارد. اگر روزی کتابخانه عوض شود، فقط این تابع تغییر میکند.
- تست: `tests/test_planning.py::test_recurrence_expansion` (خروجی دقیق تاریخها).
- مسیر بازگشت: حذف وابستگی و جایگزینی تابع، بدون تغییر API.

**نتیجه تست:** ✅ pass — `FREQ=WEEKLY;BYDAY=MO,WE` از 2026-10-27 →
`2026-10-28, 2026-11-02, 2026-11-04, 2026-11-09`.

## ۴) سیستم پایدار Skill Intelligence

`app/skills/registry.py` + جدول `skills` / `skill_usage`:

- **فهرست مرکزی:** ۱۲ کاندیدا با منبع، نسخه، commit (در صورت وجود)، مجوز، ریسک،
  دسترسیها، امتیاز و وضعیت.
- **امتیازدهی قابلتکرار:** مجوز ۲۵ + نگهداری ۲۰ + امنیت ۲۰ + تناسب ۲۰ + هزینه وابستگی ۱۵.
  مجوز نامشخص یا دسترسی پرریسک → **وتوی سخت** (`sandbox_check`).
- **تشخیص تکراری:** `slug` یکتا؛ `seed` بهصورت idempotent بهروزرسانی میکند.
- **سازگاری با متخصصها:** `domain` و `required_permissions` ثبت میشوند.
- **فعالسازی/غیرفعالسازی/بازگشت:** فقط با مجوز مجاز، ریسک ≤ متوسط، تست `pass`؛
  `rollback` نسخه قبلی را برمیگرداند.
- **گزارش خطا و استفاده:** `skill_usage` هر activate/deactivate/rollback/reject را ثبت میکند.
- **SBOM:** `GET /api/v1/skills/sbom` → `docs/SBOM.md`.

### محدودیت امنیتی عمدی

هیچ کد خارجی در این سیستم **اجرا نمیشود**. `sandbox_check` فقط بررسی ایستای
قابلیتها و نشانههای مشکوک انجام میدهد. محتوای فایلهای مهارت بهعنوان «داده
غیرقابلاعتماد» در نظر گرفته میشود، نه دستورالعمل. بهروزرسانی خودکار وابستگیها و
نصب خودکارSkills ممنوع است.

## ۵) مجوزها و انطباق

- لیست مجاز: MIT, Apache-2.0, BSD-3-Clause, BSD-2-Clause, ISC, MPL-2.0, Zlib،
  و ترکیب تأییدشده `Apache-2.0 OR BSD-3-Clause`.
- `NOASSERTION` / خالی / `CC-BY-4.0` (برای کد) → توقف تا بررسی حقوقی.
- GPL/AGPL در این فاز بررسی نشدند؛ در صورت نیاز به ادغام، سازگاری با توزیع
  و تجاریسازی باید جداگانه ارزیابی شود.
- اعتبار سازندگان حفظ شده؛ هیچ کد خارجی بهعنوان تولید اختصاصی رومکا معرفی نشده است.

## ۶) چرخه بهبود دورهای (پیشنهاد)

1. هر ماه: پرسوجوی GitHub API برای کاندیداهای مرتبط با شکافهای فعلی.
2. بررسی `pushed_at`، `license`، وابستگیها و آسیبپذیریها (`pip-audit`).
3. اجرای `evaluate_candidate` + `sandbox_check` در محیط ایزوله.
4. نمونه اولیه محدود + تست؛ مقایسه اثر واقعی (زمان پاسخ، خطا، اندازه کد).
5. فقط تغییرات کمخطر، دارای مجوز روشن و قابل آزمون، آنهم با تأیید انسانی ادغام شوند.

## ۷) منابع ردشده و درس آموخته

مهمترین درس: **ستارههای زیاد ≠ مناسب بودن**. `crewAI` و `mem0` پروژههای باکیفیتیاند،
ولی درخواست دسترسی گسترده یا انتقال داده شخصی به سرویس خارجی، هزبنهٔ امنیتی آنها
را از ارزششان بیشتر میکند. در فاز فعلی، «یک مدل + ابزارهای مناسب + اورکستریشن
قطعی» قابلاعتمادتر است.
